# Domain Content Map — Design Systems for Data Products: Components, Tokens, and Governance

Read this during Phase 3 (architecture) and Phase 4 (writing) of the module
development workflow. Verify all factual claims and numbers against the
authoritative sources before publishing (Phase 2 evidence base); flag
anything disputed rather than repeating it.

## Absorbed capabilities this module must produce
1. Architect design systems for data products through token layers (perceptually-verified palette, semantic color, typographic, motion, geometry tokens with multi-platform delivery), chart-component libraries (taxonomy spanning charts, composites, containers, and data states with accessibility-honesty defaults baked into APIs, headless-plus-themed composition, documentation with selection guidance), pattern-template layers (dashboard, interaction, and page assemblies with composition rules), and encoding-guidance systems (chart-selection matrices, integrity rules, automated lint enforcement), govern through ownership models, visual-inclusive semantic versioning with codemods, adoption tracking, justified-exception processes, and Figma-code parity, engineer theming (brand integration under perceptual constraints, theme variants preserving hierarchy, cross-theme audits).
2. Measure and evolve via system-health metrics, consumer feedback, and evidence-driven roadmaps.
3. Diagnose zombie-rigidity-quality-version-governance failures, and scale through federated architectures, platform coexistence, rollout strategies, and enterprise governance structures.

## Unit 1 — Unit 1

**Scope:** Covers the scalable-consistency discipline: the design-system case for data products — the scale argument: the consistency-at-scale problem (the multi-dashboard, multi-team, multi-product divergence — the same-metric-different-visual chaos, the user-relearning cost per inconsistency), the velocity-and-quality argument (the reusable-component acceleration — the compose-don't-rebuild discipline, the baked-in quality: the accessibility, honesty, and performance standards embedded per component rather than re-decided per chart), the data-product-specific system challenges (the data-driven variability — the components adapting to arbitrary datasets versus fixed-content UI components, the encoding-decision systematization — the color-scale-and-chart-type rules as system citizens, the freshness-and-state complexity — the loading, empty, error, and stale states as first-class system concerns) as the systems rationale; the design-token architecture — the atomic layer: the visualization-token families (the color-token systems — the categorical, sequential, and diverging palette tokens with the perceptual-and-CVD verification baked in, the semantic-color tokens — the success-warning-danger-info families for status encoding, the neutral-and-chrome scales), the typographic-and-spacing tokens (the chart-text hierarchies — the title, label, tick, and annotation type scales, the panel-and-grid spacing systems from the layout discipline), the motion-and-transition tokens (the duration-and-easing standards — the coordinated-animation vocabulary, the reduced-motion token variants), the chart-geometry tokens (the mark-size-and-stroke-weight scales, the axis-and-gridline style standards, the corner-radius-and-shadow conventions), and the token-delivery mechanisms (the multi-platform token pipelines — the CSS-variables, JS-objects, and Figma-variables synchronization, the dark-mode-and-theme token architectures) as the atomic system; the chart-component-library architecture — the reusable layer: the component taxonomy (the chart-type components — the bar, line, scatter, and area families with the configuration APIs, the composite components — the KPI-tiles, sparklines, bullet-graphs, gauges, the container components — the panels, legends, filter-rails, tooltip-shells, the state components — the loading skeletons, empty states, error boundaries for data contexts), the component-API design (the data-in-visual-out contracts — the props-and-slots architecture from the component-architecture discipline: the sensible-defaults-with-full-override philosophy, the accessibility-and-honesty defaults baked in — the alt-text structure, axis integrity, and reduced motion as component behavior), the composition patterns (the primitive-versus-configurable component spectrum — the visx-style composition versus the config-driven charts, the headless-core-plus-themed-wrappers architecture from the framework discipline), and the component-documentation standards (the live-example galleries with data variants, the when-to-use-and-when-not-to-use guidance — the chart-selection support embedded in docs, the do-and-don't comparisons with perceptual rationale) as the component system; the pattern-and-template layer — the assembled structures: the dashboard templates (the pre-composed layouts — the KPI-row-plus-grid starter structures with the zoning discipline embedded, the genre templates: the executive, operational, and analytic starters from the dashboard discipline), the interaction-pattern libraries (the filter-panel, drill-down, tooltip, and cross-view-linking standard implementations — the coordinated-behavior components, the navigation-pattern components from the wayfinding discipline), the page-and-view templates (the analysis-workspace, detail-page, and report-view skeletons), and the pattern documentation (the usage-context-and-variant guidance, the pattern-composition rules — the which-patterns-combine-well knowledge) as the assembled layer; the encoding-and-chart-selection guidance — the decision-support layer: the chart-selection systems (the data-type-and-task-to-chart-type decision trees and matrices — the embedded guidance in docs and tooling, the chart-type deprecation-and-discouragement lists — the pie-and-3D restraint rules from the honesty disciplines), the encoding-rule systems (the color-usage rules — the semantic-reservation-and-categorical-limits, the axis-and-scale integrity rules — the zero-baseline-and-truncation discipline as system policy, the size-and-position encoding conventions), the accessibility-encoding requirements (the contrast minimums, CVD-safe palette mandates, redundant-encoding rules as system constraints), and the guidance-enforcement mechanisms (the lint-and-validation tooling for chart configs — the automated honesty-and-accessibility checks, the design-review checklist integration) as the decision layer; the governance-and-stewardship — the organizational layer: the system-ownership models (the central-team versus federated stewardship — the data-viz-guild patterns, the contribution-and-review workflows for new components), the versioning-and-release discipline (the semantic-versioning-for-visual-systems — the breaking-change taxonomy including visual-output changes from the component discipline, the migration guides and codemods, the deprecation windows and sunset processes), the adoption-and-compliance management (the system-adoption tracking — the usage analytics across products, the exception-and-escape-hatch processes — the justified-deviation documentation, the legacy-migration support), the cross-team alignment (the design-engineering-analytics collaboration on system evolution, the stakeholder communication of system value and standards), and the Figma-code parity systems (the design-file-and-implementation synchronization — the token-and-component parity verification, the design-handoff workflows) as the governance system; the theming-and-brand integration — the adaptation layer: the brand-theme architecture (the organization identity within system constraints — the brand-color integration with perceptual verification, the white-label-and-multi-brand support patterns), the theme-variant systems (the light-dark-and-high-contrast themes with relationship preservation from the hierarchy discipline, the density-and-scale theme variants — the compact, comfortable, and spacious modes), the data-viz-specific theming challenges (the palette generation under brand constraints — the perceptually-valid ramps from brand hues, the theme-switching state preservation for live dashboards), and the theme-testing-and-verification (the cross-theme accessibility-and-legibility audits, the visual-regression testing across theme matrices from the QA discipline) as the theming system; the system-measurement-and-evolution — the improvement layer: the system-health metrics (the adoption-and-coverage measurement — the component-usage rates across products, the consistency-audit results — the deviation detection across dashboards, the quality metrics — the accessibility-and-performance compliance rates via automated checks), the user-and-developer-experience feedback (the system-consumer satisfaction surveys — the designer-and-engineer experience assessment, the friction-and-gap identification from support channels), the evidence-driven evolution (the usage analytics informing component-and-pattern priorities — the deprecate-improve-invest decisions, the perceptual-and-usability-research integration into system updates), and the system-roadmap management (the capability-gap planning — the missing-chart-types-and-patterns roadmap, the technology-evolution integration — the new-framework-and-rendering capability adoption) as the evolution practice; the design-system failure modes — the diagnostic library: the zombie-system failure (the documented-but-unadopted system — the ivory-tower component libraries ignored by teams, the adoption-incentive-and-velocity-proof gaps), the rigidity failure (the over-constrained systems blocking legitimate needs — the escape-hatch absence driving shadow systems), the consistency-without-quality failure (the uniformly-mediocre components — the system amplifying bad defaults at scale, the baked-in honesty-and-accessibility absence), the version-chaos failure (the uncontrolled divergence across product versions — the migration-support absence), and the governance-vacuum failure (the ownerless system decay — the contribution-and-review collapse) with the repair patterns as the diagnostic discipline; the multi-product-and-enterprise-scale patterns — the enterprise layer: the federated-system architectures (the core-system-plus-domain-extensions — the analytics-team-specific layers on shared foundations, the multi-product-family coordination), the enterprise-analytics-platform integration (the BI-tool-and-custom-system coexistence — the design parity across platforms, the embedded-analytics theming), the organizational-rollout strategies (the pilot-and-champion adoption models, the migration-wave planning for legacy dashboards), and the enterprise-governance structures (the design-system councils and working groups, the standards-and-policy integration with compliance requirements) as the enterprise practice; and the design-systems deliverable — the token-component-pattern-governance system capability for consistent data products at scale.
