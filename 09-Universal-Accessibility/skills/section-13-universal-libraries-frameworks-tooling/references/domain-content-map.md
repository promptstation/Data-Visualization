# Domain Content Map — Libraries, Frameworks, and Tooling: The Accessible Visualization Ecosystem

Read this during Phase 3 (architecture) and Phase 4 (writing) of the module
development workflow. Verify all factual claims and numbers against the
authoritative sources before publishing (Phase 2 evidence base); flag
anything disputed rather than repeating it.

## Absorbed capabilities this module must produce
1. Navigate the accessible visualization ecosystem by evaluating charting libraries against a semantics-keyboard-description-evidence-documentation rubric (Highcharts module depth, D3 full-responsibility reality, middle-tier variance, BI platform procurement postures).
2. Integrate at the framework layer (React-Vue-Svelte ARIA and focus management, server-rendered and email table fallbacks, accessible wrapper component strategy with design system sanction, component-level test assertions), compose the testing toolchain (axe-core CI integrations, custom chart-domain rules, cross-platform screen reader environments, CVD simulators and contrast and focus inspectors, stack assembly by team maturity), wield color and design instruments (ColorBrewer-Okabe-Ito-viridis palette sources.
3. Design-time simulation plugins, token pipelines, description generation with human review, notebook accessibility), and prevent library-worship, tool-fragmentation, scanner-dependency, plugin-rot, simulation-complacency, and export-blindness failures.

## Unit 1 — Unit 1

**Scope:** Covers the ecosystem layer: the charting library accessibility survey — the capability landscape: the Highcharts accessibility tradition (the dedicated accessibility module as the most complete commercial implementation: the automatic SVG proxy layer that builds a parallel accessible DOM over the chart, the built-in screen reader announcements for series and points, the keyboard navigation module with configurable traversal modes, the sonification add-on connecting to the audio systems of section 5, and the extensive accessibility documentation as an industry reference); the D3 ecosystem reality (the no-built-in-accessibility truth of the low-level toolkit: the full responsibility on the implementer using the semantics, ARIA, and description techniques from sections 4 and 5, the community patterns and reusable accessible chart components that have emerged, and the advantage that nothing prevents best-practice implementation because every layer is under control); the middle-tier libraries (the ECharts, Chart.js, Plotly, and ApexCharts accessibility features at survey depth: the canvas-based libraries and their text alternative strategies, the ARIA support levels, the keyboard interaction provisions, and the wide variance in quality that demands per-library evaluation); the commercial and no-code tools (the Tableau, Power BI, Flourish, and Datawrapper accessibility postures: the screen reader support levels, the keyboard operability, the accessible export options, and the procurement evaluation criteria for BI platforms from the governance preview); and the evaluation framework for library selection (the semantics, keyboard, description, testing evidence, documentation, and maintenance activity criteria synthesized into a selection rubric) as the library landscape; the framework integration layer — the application context: the React accessibility integration (the JSX and ARIA property mapping, the focus management libraries like react-focus-lock and the React Aria component traditions, the SVG chart component patterns with accessible props, and the virtual DOM re-render implications for live regions and focus preservation from section 11); the Vue and Svelte integration (the template directive equivalents for ARIA binding, the framework-specific focus and transition considerations, and the component library options); the server-rendered and static contexts (the HTML email chart accessibility with table-based fallbacks, the static site generator integration for journalistic and report visualizations, and the PDF generation pipelines connecting to section 10); the wrapper component strategy (the accessible-chart-wrapper pattern: the team-built component that bundles semantics, descriptions, keyboard behavior, and testing around any base library, the design system integration where the wrapper becomes the sanctioned path from section 14, and the maintenance burden of wrappers versus native library support); and the framework testing integration (the component-level accessibility assertions in Jest and Vitest suites using jest-axe and testing-library queries, the story and fixture driven accessibility regression from the design system traditions) as the application layer; the testing toolchain — the verification instruments: the automated scanners in depth (the axe-core engine and its integrations: the Lighthouse, WAVE, ARC Toolkit, and pa11y family surveyed in section 12 with the CI integration patterns via GitHub Actions and pre-commit hooks), the scanner rule customization for chart domains (the custom rule authoring for data-attribute conventions and SVG semantics checks from section 12); the screen reader testing environments (the NVDA plus Firefox and JAWS plus Chrome Windows combinations, the VoiceOver plus Safari macOS and iOS combinations, the TalkBack plus Chrome Android combinations, and the virtual machine and device lab provisioning strategies); the specialized visualization checkers (the contrast checking tools for graphical objects, the color vision deficiency simulators like Color Oracle and the Stark plugin family, the keyboard traversal mappers and focus order visualizers, and the accessibility tree inspectors in browser DevTools from section 3); and the toolchain composition (the recommended stack assembly by team size and maturity: the scanner plus manual protocol baseline through the full triad instrumentation of section 12) as the verification toolkit; the color and design tooling — the creative instruments: the palette tools (the ColorBrewer heritage for cartographic and statistical palettes, the Okabe-Ito and Tol palette distributions, the scientific colormap families including viridis and cividis with their generation tooling, the CVD simulation integrated in Figma, Sketch, and Adobe products via plugins, and the contrast checker ecosystem from WebAIM to design-tool-native checkers); the design system tooling (the token pipelines that carry verified colors and spacing into code from section 14, the Figma accessibility plugins like Stark and Able for design-time verification, and the component documentation platforms with accessibility annotation support); the description generation tools (the automated alt text services and their accuracy caveats from section 5, the template-based summary generators in BI platforms, and the AI description assistants with human review workflows); and the authoring environment accessibility (the accessible data preparation and chart building in spreadsheets and notebooks: the Jupyter and R Markdown accessibility considerations for reproducible analysis contexts) as the creative toolkit; the tooling anti-patterns — the failure library: the library worship failure (the assumption that a popular library is accessible by default producing unexamined inherited barriers, remedied by the evaluation rubric and independent testing); the tool fragmentation failure (the dozen disconnected checkers with no integration or ownership, remedied by the composed toolchain with clear pipeline placement); the scanner dependency failure (the automated-only verification from section 12 repeated at the tooling level, remedied by triad instrumentation); the plugin rot failure (the abandoned accessibility plugins and wrappers breaking silently on framework upgrades, remedied by maintenance activity evaluation and regression testing); the simulation complacency failure (the CVD filter passing treated as real-user validation from section 6, remedied by user testing requirements); and the export blindness failure (the accessible on-screen chart with inaccessible PDF, email, and image exports, remedied by the deliverable-format coverage checks of section 10) with detection methods as the diagnostic discipline; and the tooling deliverable — the evaluated library selection, framework integration, testing verification, and creative color-description instrument stack supporting every other section of this course.
