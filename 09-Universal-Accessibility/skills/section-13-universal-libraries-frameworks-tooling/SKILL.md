# Libraries, Frameworks, and Tooling: The Accessible Visualization Ecosystem — Professional Training

## Mission

Produce professional-grade learning modules and training materials on **libraries, Frameworks, and Tooling: The Accessible Visualization Ecosystem** within Inclusive visualization engineering — WCAG fluency, assistive-technology partnership, and accessible-by-architecture chart, dashboard, and interaction design serving users with visual, motor, and cognitive disabilities.

Subject scope: Covers the ecosystem layer: the charting library accessibility survey — the capability landscape: the Highcharts accessibility tradition (the dedicated accessibility module as the most complete commercial implementation: the automatic SVG proxy layer that builds a parallel accessible DOM over the chart, the built-in screen reader announcements for series and points, the keyboard navigation module with configurable traversal modes, the sonification add-on connecting to the audio systems of section 5, and the extensive accessibility documentation as an industry reference); the D3 ecosystem reality (the no-built-in-accessibility truth of the low-level toolkit: the full responsibility on the implementer using the semantics, ARIA, and description techniques from sections 4 and 5, the community patterns and reusable accessible chart components that have emerged, and the advantage that nothing prevents best-practice implementation because every layer is under control); the middle-tier libraries (the ECharts, Chart.js, Plotly, and ApexCharts accessibility features at survey depth: the canvas-based libraries and their text alternative strategies, the ARIA support levels, the keyboard interaction provisions, and the wide variance in quality that demands per-library evaluation); the commercial and no-code tools (the Tableau, Power BI, Flourish, and Datawrapper accessibility postures: the screen reader support levels, the keyboard operability, the accessible export options, and the procurement evaluation criteria for BI platforms from the governance preview); and the evaluation framework for library selection (the semantics, keyboard, description, testing evidence, documentation, and maintenance activity criteria synthesized into a selection rubric) as the library landscape; the framework integration layer — the application context: the React accessibility integration (the JSX and ARIA property mapping, the focus management libraries like react-focus-lock and the React Aria component traditions, the SVG chart component patterns with accessible props, and the virtual DOM re-render implications for live regions and focus preservation from section 11); the Vue and Svelte integration (the template directive equivalents for ARIA binding, the framework-specific focus and transition considerations, and the component library options); the server-rendered and static contexts (the HTML email chart accessibility with table-based fallbacks, the static site generator integration for journalistic and report visualizations, and the PDF generation pipelines connecting to section 10); the wrapper component strategy (the accessible-chart-wrapper pattern: the team-built component that bundles semantics, descriptions, keyboard behavior, and testing around any base library, the design system integration where the wrapper becomes the sanctioned path from section 14, and the maintenance burden of wrappers versus native library support); and the framework testing integration (the component-level accessibility assertions in Jest and Vitest suites using jest-axe and testing-library queries, the story and fixture driven accessibility regression from the design system traditions) as the application layer; the testing toolchain — the verification instruments: the automated scanners in depth (the axe-core engine and its integrations: the Lighthouse, WAVE, ARC Toolkit, and pa11y family surveyed in section 12 with the CI integration patterns via GitHub Actions and pre-commit hooks), the scanner rule customization for chart domains (the custom rule authoring for data-attribute conventions and SVG semantics checks from section 12); the screen reader testing environments (the NVDA plus Firefox and JAWS plus Chrome Windows combinations, the VoiceOver plus Safari macOS and iOS combinations, the TalkBack plus Chrome Android combinations, and the virtual machine and device lab provisioning strategies); the specialized visualization checkers (the contrast checking tools for graphical objects, the color vision deficiency simulators like Color Oracle and the Stark plugin family, the keyboard traversal mappers and focus order visualizers, and the accessibility tree inspectors in browser DevTools from section 3); and the toolchain composition (the recommended stack assembly by team size and maturity: the scanner plus manual protocol baseline through the full triad instrumentation of section 12) as the verification toolkit; the color and design tooling — the creative instruments: the palette tools (the ColorBrewer heritage for cartographic and statistical palettes, the Okabe-Ito and Tol palette distributions, the scientific colormap families including viridis and cividis with their generation tooling, the CVD simulation integrated in Figma, Sketch, and Adobe products via plugins, and the contrast checker ecosystem from WebAIM to design-tool-native checkers); the design system tooling (the token pipelines that carry verified colors and spacing into code from section 14, the Figma accessibility plugins like Stark and Able for design-time verification, and the component documentation platforms with accessibility annotation support); the description generation tools (the automated alt text services and their accuracy caveats from section 5, the template-based summary generators in BI platforms, and the AI description assistants with human review workflows); and the authoring environment accessibility (the accessible data preparation and chart building in spreadsheets and notebooks: the Jupyter and R Markdown accessibility considerations for reproducible analysis contexts) as the creative toolkit; the tooling anti-patterns — the failure library: the library worship failure (the assumption that a popular library is accessible by default producing unexamined inherited barriers, remedied by the evaluation rubric and independent testing); the tool fragmentation failure (the dozen disconnected checkers with no integration or ownership, remedied by the composed toolchain with clear pipeline placement); the scanner dependency failure (the automated-only verification from section 12 repeated at the tooling level, remedied by triad instrumentation); the plugin rot failure (the abandoned accessibility plugins and wrappers breaking silently on framework upgrades, remedied by maintenance activity evaluation and regression testing); the simulation complacency failure (the CVD filter passing treated as real-user validation from section 6, remedied by user testing requirements); and the export blindness failure (the accessible on-screen chart with inaccessible PDF, email, and image exports, remedied by the deliverable-format coverage checks of section 10) with detection methods as the diagnostic discipline; and the tooling deliverable — the evaluated library selection, framework integration, testing verification, and creative color-description instrument stack supporting every other section of this course.

Write as an experienced practitioner, not as a summarizer of popular content. Every framework taught must be something a real team or professional could run: procedures they can execute, criteria they can judge with, and artifacts they can hand to a colleague. Do not present claims as settled when the field treats them as contested — the training must model evidence discipline.

The module deepens this section's capabilities for a learner progressing from competent beginner toward expert practitioner, and connects them to the surrounding discipline rather than teaching them in isolation.

## Use Cases

### Full learning module
When asked for a comprehensive module on this topic:
1. Scope audience, prerequisites, duration, and discipline mix.
2. Build the evidence base from the authoritative sources below.
3. Write the full progressive module from the template.
4. Include all exercises with model solutions and all gate checklists.
5. Validate against the gate below before delivery.

### Condensed workshop
When asked for a one-day or half-day workshop:
1. Prioritize the units that match where the group is stuck.
2. Compress content to frameworks plus one worked example each; run exercises live with the participants' own material.
3. Leave behind the relevant checklists as job aids.

### Working job aids
When a practitioner needs tools rather than teaching:
1. Deliver the applicable checklists and templates from `references/exercise-and-checklist-library.md`, customized to their situation.
2. Add a one-page rationale per aid so the user understands what each item protects against.

## Core Output Requirements

- Deliverables are Markdown documents: the module, exercise sets with model solutions, and checklists. No placeholders, no "TODO" sections.
- Ground content in authoritative sources:
- The WCAG 2.1/2.2 specification and Understanding documents with the W3C WAI tutorials and ARIA authoring practices
- The WAI-Graphics and WAI-ARIA Graphics Module work (graphics-symbol, graphics-object, graphics-document roles) and the W3C SVG accessibility guidance
- The DIAGRAM Center and AEM/Accessible Educational Materials research on accessible complex graphics, charts, and data tables
- The data-sonification and audio-graph literature (the highcharts-sonification-style practice and research traditions) plus descriptive-text standards for charts
- The color-vision-deficiency research tradition (the Okabe-Ito palette, ColorBrewer lineage, CVD simulation tooling documentation)
- Nielsen Norman Group and WebAIM accessibility research including the WebAIM Million automated-analysis findings
- The regulatory landscape documents (the ADA, Section 508, and the European Accessibility Act requirements) with the EN 301 549 standard
- Maintain an evidence ledger while writing: every factual claim or number is either sourced, flagged as disputed/popular account, or omitted. Never invent statistics, studies, or citations.
- Distinguish established research findings from professional conventions and informed recommendations, and say which is which.
- Explain each specialized term in clear language on first use.

## Writing Standards

Throughout the material, prioritize language that is:

* Precise without becoming jargon-heavy
* Practical without discarding rigor
* Honest about limitations and contested findings without being defeatist
* Concrete — anchored in real cases, real artifacts, and verifiable numbers
* Progressive from fundamentals to expert judgment

Where a recommendation depends on context, explain the trade-off rather than presenting an absolute rule.

## Anti-Patterns

Avoid: Overlay-widget delusion — bolting on an accessibility-toolbar plugin while the underlying charts remain inaccessible; overlays treating symptoms while the architecture excludes; Alt-text theater — 'Chart. Bar chart.' descriptions that name the graphic type but convey none of the data insight, satisfying tools while failing users; Color-only encoding — meaning carried exclusively by hue with no luminance, pattern, label, or position redundancy, excluding CVD and monochrome users silently; Keyboard trap charts — interactive visualizations reachable only by pointer, with no focus path, no keyboard operation of brushes or drill-downs, and no focus-visible indication; Compliance-checklist ceiling — passing automated scans (which catch a minority of real barriers) and declaring victory without screen-reader sessions, disabled-user testing, or task-completion evidence; exercises without evaluation criteria; modules that stop at inspiration without a single decision the learner can now make better; and any content that overstates certainty beyond what the evidence supports.

## Decision Heuristic

When allocating depth under time or length limits, ask:

1. Where will this audience actually stall in practice?
2. Which unit protects the most value if taught well?
3. Can the learner run the framework tomorrow without me?
4. Is every example doing work a plain sentence could not?
5. What would a skeptical domain expert say about this material?

If two topics compete for space, keep the one that changes a decision.

## Final Principle

The goal is not more content about Accessibility. The goal is that a practitioner could take this material and perform: Navigate the accessible visualization ecosystem by evaluating charting libraries against a semantics-keyboard-description-evidence-documentation rubric (Highcharts module depth, D3 full-responsibility reality, middle-tier variance, BI platform procurement postures), design-time simulation plugins, token pipelines, description generation with human review, notebook accessibility), and prevent library-worship, tool-fragmentation, scanner-dependency, plugin-rot, simulation-complacency, and export-blindness failures — with the same evidence discipline the field's best practitioners use. The module must function simultaneously as a learning resource, a practical reference, and a working methodology.
