# Domain Content Map — Keyboard, Focus, and Motor Accessibility: Operable Visualization

Read this during Phase 3 (architecture) and Phase 4 (writing) of the module
development workflow. Verify all factual claims and numbers against the
authoritative sources before publishing (Phase 2 evidence base); flag
anything disputed rather than repeating it.

## Absorbed capabilities this module must produce
1. Engineer keyboard-operable visualization through the full-task-path standard (every filter-drill-compare-export journey keyboard-reachable) with focus management systems (single-stop-roving-versus-per-mark models, logical focus ordering with skips and groups, high-visibility indicators distinguished across states, focus preservation-restoration through dynamic updates, trap discipline with escape guarantees).
2. Translate pointer interactions to keyboard equivalents (focus-triggered tooltips and cursor navigation, form-based brush alternatives, zoom-pan controls and semantic commands, menu-move drag replacements, systematic gesture audits), serve motor diversity beyond keyboard (24-44px targets with density-tension solutions, precision tolerance via expanded hit areas and error correction, adjustable timing without time pressure, switch-voice-head-pointer compatibility, fatigue-reducing shortcuts-persistence-batching).
3. Build accessible control components per APG patterns (filters, sortable tables, chart actions, custom-widget verification.
4. Design-system sourcing), document keyboard support through in-context instructions, maps, discoverability signaling, and feedback channels, prevent pointer-only-focus-invisible-trap-tab-explosion-focus-loss-tiny-target-timeout-undocumented anti-patterns.
5. Validate via unplug-the-mouse testing, AT-combination verification, motor-disabled user partnerships, and automated traversal audits with manual complement.
